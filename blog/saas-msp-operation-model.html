운영 모델

SaaS 운영형 계약(MSP) 모델: 지속 가능한 운영 구조 만들기

시스템은 오픈한 날부터 운영이 시작됩니다. 운영형 계약(MSP)은 고객사에는 예측 가능한 운영 비용과 품질을, 공급사에는 장기적인 관계를 만들어 줍니다. 계약 범위와 SLA를 어떻게 정의해야 하는지 정리했습니다.

오노퍼스 엔지니어링팀 발행 2025.01.25 수정 2026.11.11 읽는 시간 약 10분

MSP 모델이 필요한 이유

프로젝트로 시스템을 구축한 뒤 고객사가 직접 운영하면 다음과 같은 문제가 자주 생깁니다.

  • 전문 인력 부족: DevOps, 보안, 성능 튜닝을 맡을 사람이 내부에 없습니다.
  • 장애 대응 지연: 모니터링과 대응 절차가 없어 장애를 고객 문의로 처음 알게 됩니다.
  • 점진적 성능 저하: 데이터가 쌓이면서 느려지지만 아무도 원인을 보지 않습니다.
  • 보안 공백: 라이브러리와 서버의 보안 패치가 밀립니다.

운영형 계약(MSP, Managed Service Provider)은 이 일을 월 단위 계약으로 맡겨, 시스템이 오픈 이후에도 계속 관리되고 개선되도록 하는 방식입니다.

서비스 범위 정의

MSP 계약에서 가장 중요한 것은 무엇이 포함되고 무엇이 별도인지를 명확히 하는 것입니다.

모니터링과 알림

CPU·메모리·디스크 사용률, API 응답 시간, 에러율 같은 지표를 실시간으로 수집하고, 임계값을 넘으면 담당자에게 알림을 보냅니다. 반복되는 단순 장애는 자동 복구 스크립트로 처리합니다.

장애 대응과 복구

장애를 등급으로 나누고 등급별 초기 대응·복구 목표 시간을 정합니다. 장애가 끝나면 근본 원인 분석(RCA) 보고서를 작성하고 재발 방지 조치를 기록합니다.

성능 최적화

월 또는 분기 단위로 성능을 분석하고 병목을 개선합니다. 쿼리 튜닝, 캐시 전략 조정, 인프라 자원 조정 등이 포함됩니다.

보안 패치와 규제 대응

취약점 공지를 모니터링해 패치를 적용하고, 정기적으로 보안 점검을 수행합니다. 개인정보 보호법 등 관련 규제 변경이 있으면 시스템 반영 범위를 함께 검토합니다.

AI 기능 고도화

운영 데이터를 바탕으로 문서 처리 자동화, 고객 응대 보조, 데이터 분석 자동화 같은 기능을 단계적으로 추가합니다.

SLA 정의와 측정

서비스 수준 협약(SLA)은 측정 가능한 숫자로 정의해야 분쟁이 없습니다.

가용성(Uptime)

월 99.9%는 30일 기준 약 43분, 99.95%는 약 22분의 비계획 중단을 허용한다는 뜻입니다. 사전에 공지한 정기 점검 시간은 보통 계산에서 제외하며, 측정 방법(외부 헬스체크 주기 등)도 함께 정해 둡니다.

응답 시간

평균보다 p95(상위 5% 느린 요청) 기준이 사용자 경험을 더 잘 반영합니다. 예: "핵심 API 요청의 95%가 500ms 이내에 응답".

장애 등급별 대응 목표

등급예시초기 대응 목표(예시)복구 목표(예시)
P1 치명서비스 전체 중단, 데이터 손실 위험24/7 계약 시 1시간 이내4시간 이내 임시 복구
P2 중요핵심 기능 일부 장애업무 시간 4시간 이내1영업일 이내
P3 일반우회 가능한 오류, 경미한 성능 저하1영업일 이내정기 배포에 포함

위 수치는 설명을 위한 예시입니다. 실제 목표는 시스템의 중요도와 계약 등급에 따라 협의해 정합니다.

SLA 미달 시 보상

목표에 미달하면 다음 달 운영비의 일정 비율을 감액하는 서비스 크레딧 방식이 일반적입니다. 보상 상한과 예외 사유(고객사 측 원인, 클라우드 제공사 장애 등)도 함께 명시합니다.

비용 구조 설계

월 고정 비용

모니터링, 정기 점검, 월간 리포트 같은 기본 운영은 월 고정 비용으로 정해 고객이 운영 예산을 예측할 수 있게 합니다.

추가 작업 비용

성능 개선 프로젝트, 신규 기능, 계약 범위를 넘는 긴급 대응 등은 별도로 산정하거나, 월 일정 시간의 개선 작업을 포함한 등급(Lite / Standard / Enterprise)으로 묶어 제공합니다.

인프라 비용

클라우드 비용은 고객 계정에서 직접 결제하는 방식과 운영사가 대신 관리·청구하는 방식이 있습니다. 어느 쪽이든 월간 리포트에 비용 추이와 절감 제안을 포함하면 운영사가 비용 최적화를 책임지는 구조가 됩니다.

운영 프로세스와 도구

  • 모니터링: Prometheus·Grafana, Datadog, New Relic 등으로 지표를 수집·시각화하고, Slack·PagerDuty 등으로 알림을 전달합니다.
  • 이슈 관리: Jira, Linear 같은 도구로 장애·개선·요청을 관리하고, 고객사도 진행 상황을 확인할 수 있게 합니다.
  • 정기 리포트: 가용성, 성능 지표, 장애 내역, 처리한 개선 작업, 다음 달 계획을 월 단위로 공유합니다.

계약 전 체크리스트

  1. 운영 대상 시스템과 범위(애플리케이션, 인프라, DB, 외부 연동)가 목록으로 정리되어 있는가
  2. 장애 등급 정의와 등급별 대응·복구 목표가 합의되었는가
  3. 대응 시간대(업무 시간 / 24시간)와 연락 체계가 정해졌는가
  4. 포함 작업과 별도 비용 작업의 경계가 명확한가
  5. 리포트 주기와 항목, 정기 회의 일정이 정해졌는가
  6. 계약 종료 시 인수인계(문서, 계정, 접근 권한) 절차가 있는가
