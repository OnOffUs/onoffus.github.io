AI SaaS 아키텍처 설계: 확장 가능한 구조 만들기

AI 기능을 포함한 B2B SaaS는 일반 웹 애플리케이션보다 구성 요소가 많고, 외부 모델 API라는 통제하기 어려운 의존성까지 생깁니다. AI 추론, 벡터 검색, 데이터 파이프라인을 안정적으로 통합하는 설계 원칙을 실무 관점에서 정리합니다.

AI SaaS를 구성하는 요소

AI 기능이 들어간 SaaS는 일반 웹 서비스보다 움직이는 부분이 많습니다. 대표적인 구성 요소는 다음과 같습니다.

  • API 게이트웨이: 인증, 테넌트 식별, 요청 속도 제한을 한곳에서 처리
  • 핵심 비즈니스 서비스: 사용자·권한·과금 등 SaaS의 기본 기능
  • AI 추론 서비스: LLM API 또는 자체 모델 호출, 프롬프트·모델 버전 관리
  • 검색 계층: 벡터 DB와 키워드 검색을 결합한 RAG 검색
  • 데이터 파이프라인: 문서 수집, 정제, 임베딩, 색인 갱신
  • 관측성: 로그·메트릭·트레이스와 AI 호출 단위의 비용·품질 지표

이 요소들을 처음부터 모두 별도 서비스로 만들 필요는 없습니다. 다만 경계를 명확히 해 두면 나중에 필요한 부분만 분리하기 쉽습니다.

서비스 경계와 데이터 계약

도메인 경계를 명확히 하고 서비스 간에 주고받는 데이터의 형식(데이터 계약)을 문서화하면 변경 비용이 크게 줄어듭니다. 특히 이벤트를 주고받는 구조에서는 이벤트 스키마에 버전을 붙이고, 하위 호환을 지키는 규칙(필드 추가는 허용, 삭제·의미 변경은 새 버전)을 팀 전체가 공유해야 합니다.

서비스 간 통신은 모두 비동기일 필요는 없습니다. 사용자가 즉시 결과를 기다리는 조회는 동기 API로, 결과를 나중에 받아도 되는 작업과 여러 서비스가 반응해야 하는 사건은 이벤트로 처리하는 식으로 성격에 맞게 나눕니다.

이벤트 드리븐 구조와 비동기 추론

AI 추론은 수 초에서 수십 초가 걸릴 수 있어 동기 요청으로 처리하면 타임아웃과 연결 고갈이 생기기 쉽습니다. 사용자가 분석을 요청하면 작업 ID를 바로 반환하고, 백그라운드에서 처리한 뒤 결과를 알림·웹훅·폴링으로 전달하는 방식이 안정적입니다. 대화형 응답처럼 즉시성이 중요한 경우에는 스트리밍 응답으로 체감 대기 시간을 줄입니다.

Kafka 같은 이벤트 스트림을 쓰면 여러 서비스가 같은 이벤트를 구독해 각자의 일을 할 수 있습니다. 예를 들어 문서가 업로드되면 색인 갱신, 요약 생성, 알림 발송이 서로를 기다리지 않고 병렬로 실행됩니다. 이때 같은 이벤트가 두 번 처리되어도 결과가 같도록 멱등성을 보장하는 것이 중요합니다.

멀티테넌시: 데이터, 벡터 인덱스, 모델

관계형 데이터는 tenant_id 기반 공유 스키마나 테넌트별 스키마로 격리합니다. AI 기능이 들어가면 여기에 두 가지가 더 생깁니다.

  • 벡터 인덱스 격리: 테넌트별 네임스페이스·컬렉션을 분리하거나, 공유 인덱스라면 검색 시 테넌트 필터를 반드시 강제합니다. 필터 누락은 곧 다른 고객사 문서가 답변에 섞이는 사고로 이어집니다.
  • 문서 권한: 같은 고객사 안에서도 열람 권한이 다른 문서가 있습니다. 원본 시스템의 권한 정보를 색인 시점에 함께 저장하고 검색 단계에서 적용해야 합니다.
  • 모델·프롬프트: 대부분은 공통 모델에 테넌트별 프롬프트·설정을 적용하는 것으로 충분합니다. 파인튜닝은 효과가 검증된 경우에만 테넌트별로 별도 관리합니다.

멀티테넌시 격리 방식 비교는 AI 기반 B2B SaaS 구축 가이드의 멀티테넌시 장을 참고하세요.

관측성과 비용 통제

분산 환경에서 AI 기능의 병목은 대부분 추론 비용과 지연 시간입니다. 요청 단위로 다음 정보를 기록해 두면 문제를 빠르게 찾을 수 있습니다.

  • 테넌트·기능별 토큰 사용량과 비용
  • 첫 토큰까지 걸린 시간(TTFT)과 전체 응답 시간
  • 사용한 모델·프롬프트 버전
  • 검색된 문서와 답변 품질 평가 결과

이 데이터를 기준으로 캐싱, 모델 라우팅, 테넌트별 사용량 한도 같은 비용 통제 정책을 운영 기준으로 고정합니다.

장애 격리와 복구

외부 LLM API는 응답 지연, 속도 제한, 일시 장애가 생각보다 자주 발생합니다. 다음 장치를 표준으로 갖추면 장애가 전체 서비스로 번지는 것을 막을 수 있습니다.

  • 타임아웃과 재시도: 지수 백오프와 재시도 횟수 상한
  • 서킷 브레이커: 실패가 이어지면 호출을 잠시 차단하고 대체 응답 제공
  • 대체 경로: 다른 모델·제공사로 전환하거나, AI 없이도 핵심 기능이 동작하도록 설계
  • 큐 기반 처리: 일시적 장애 동안 작업을 보관했다가 복구 후 처리

복구 시나리오는 문서로만 두지 말고 실제로 장애를 주입해 검증해 보는 것이 좋습니다.

정리

좋은 AI SaaS 아키텍처는 처음부터 복잡한 구조가 아니라, 경계가 분명하고 관측 가능한 구조입니다. 무거운 작업은 비동기로, 테넌트와 문서 권한은 검색 단계까지 강제하고, 비용과 품질은 요청 단위로 측정하는 것 — 이 세 가지를 지키면 고객사가 늘어나도 시스템을 통제할 수 있습니다.
